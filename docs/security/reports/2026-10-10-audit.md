## 4. Detail Temuan

### GSPOS-SEC-009 — Error API di mode subdomain tidak memakai envelope

| Field | Isi |
|---|---|
| Severity | **High** (ketersediaan & kontrak API seluruh aplikasi Flutter di produksi; kebocoran info saat debug) |
| Kategori | A05:2021 Security Misconfiguration / Bug kontrak API |
| Status | CONFIRMED (PoC Pest + `curl` ke `api.gspos.localhost:8000`) |
| Lokasi | `app/Exceptions/ApiExceptionRenderer.php:35`, `app/Exceptions/BusinessException.php:14` |

**Root cause.** Renderer hanya aktif bila `$request->is('api/*')`. Di mode subdomain (ADR 0008, produksi `api.gspos.id/v1`)
path-nya `v1/...`, jadi renderer mengembalikan `null` dan Laravel memakai handler bawaan. `BusinessException` extends
`RuntimeException` (bukan `HttpException`), sehingga dirender sebagai 500. `SecurityHeaders::isApi()` sudah menangani host API
dengan benar, tetapi renderer tidak memakai logika yang sama.

**Dampak.**
- Semua error bisnis (`INVALID_PIN`, `PIN_LOCKED`, `SHIFT_NOT_OPEN`, `APP_UPDATE_REQUIRED`, `DISCOUNT_OVER_LIMIT`, dll.) menjadi
  `500 Server Error` tanpa `error.code`. Aplikasi Flutter tidak bisa membedakan kasus, dan force-update tidak jalan.
- 401/404/422 memakai format bawaan Laravel (`{message, errors}`), bukan envelope.
- Dengan `APP_DEBUG=true` (staging/salah konfigurasi) respons berisi `exception`, `file`, `line`, `trace` dengan path server (terbukti lokal).
- Suite test tidak menangkapnya karena test berjalan di mode satu domain.

**Reproduksi.** `tests/Feature/Security/GspoSec009ApiErrorEnvelopeSubdomainTest.php`: 4 test merah
(426 → 500; 404 & 401 tanpa `success`; trace muncul saat debug).

**Rekomendasi.** Pindahkan deteksi request API ke satu helper (mis. `Domains::isApiRequest(Request)`: `is('api/*')` atau host =
`Domains::api()`) dan pakai di `ApiExceptionRenderer` dan `SecurityHeaders`. Tambahkan test envelope mode subdomain ke CI.

**Test regresi.** `GspoSec009ApiErrorEnvelopeSubdomainTest.php` harus hijau.

### GSPOS-SEC-001 — Replay idempotency `POST /checkout` membocorkan order outlet/kasir lain

| Field | Isi |
|---|---|
| Severity | Medium (CVSS 3.1 ≈ 4.3, AV:N/AC:H/PR:L/UI:N/S:U/C:L/I:N/A:N) |
| Kategori | OWASP API1:2023 Broken Object Level Authorization |
| Status | **CONFIRMED (PoC)** |
| Lokasi | `app/Support/Idempotency.php:33`, `app/Actions/Order/CheckoutOrder.php:48-49` |

**Root cause.** `Idempotency::existing()` memakai `withoutGlobalScopes()` lalu hanya memeriksa `tenant_id`. Akibatnya `OutletScope`
(ADR 0010) terlepas dan `OrderPolicy::view` (`VisibleOrders`) tidak pernah dipanggil. `CheckoutOrder` langsung mengembalikan order
beserta `items.options` dan `payments.method`.

**Dampak.** Kasir yang mengetahui UUID order outlet lain, atau order kasir lain di luar `order.view_own`, bisa membaca isi order
lewat `POST /checkout` dengan `id` tersebut. `GET /orders/{id}` sudah menolak akses ini dengan 404. Kemungkinan rendah karena UUID
sulit ditebak, tetapi UUID bisa bocor lewat struk/QR, log, atau perangkat bersama.

**Reproduksi.** `tests/Feature/Security/GspoSec001CheckoutReplayOutletTest.php`:
- kontrol `GET /orders/{id}` = 404 ✓
- replay order outlet B oleh kasir A → **200** (harusnya 404) ✗
- replay order kasir lain di outlet yang sama → **200** ✗
- replay order sendiri = 200 ✓

**Rekomendasi.** Setelah `Idempotency::existing()` menemukan order, wajibkan `Gate::forUser($actor)->allows('view', $existing)`.
Bila gagal, lempar `NOT_FOUND`. Lebih baik lagi, tambahkan parameter callback otorisasi di `Idempotency::existing`, karena
`SaveOpenBill` memakai jalur yang sama (lihat SEC-011).

**Test regresi.** `GspoSec001CheckoutReplayOutletTest.php` hijau.

### GSPOS-SEC-002 — Lockout PIN bisa dipicu pihak lain (DoS akun)

| Field | Isi |
|---|---|
| Severity | Medium |
| Kategori | OWASP API4:2023 / A07:2021 |
| Status | **CONFIRMED (PoC)** |
| Lokasi | `app/Actions/Auth/VerifyPin.php:39-47`, `app/Actions/Auth/VerifyApproval.php:42-48`, `app/Http/Controllers/Api/V1/DeviceController.php:60-70` |

**Root cause.** Counter gagal PIN ada per user, bukan per (user, sumber). Login dan approval berbagi satu counter. Jalur approval
(`POST /orders/{id}/void`, diskon) hanya terkena `throttle:api`, bukan `throttle:auth`.

**Dampak.** Pemegang device token (perangkat dicuri, atau kasir jahat) mengambil `user_id` dari `GET /devices/{uid}/cashiers`, lalu
mengunci semua kasir dan approver selama 15 menit berulang kali. Operasional outlet berhenti, dan void/diskon tidak bisa di-approve.

**Reproduksi.** `GspoSec002PinLockoutAbuseTest.php`:
- 5 PIN salah dari perangkat penyerang → login kasir di perangkatnya sendiri **423 PIN_LOCKED**
- 5 PIN approver salah lewat void → login PIN supervisor **423**

**Rekomendasi.**
- Rate limit percobaan PIN per device/token (mis. 10 per 15 menit) sebelum counter user disentuh, ditambah notifikasi owner.
- Pisahkan counter `approval` dan `login`, atau gunakan backoff progresif.
- Catat event `pin.locked` (user, device, IP) di audit log.

**Test regresi.** `GspoSec002PinLockoutAbuseTest.php` hijau.

### GSPOS-SEC-010 — Timing oracle enumerasi email di login web & API

| Field | Isi |
|---|---|
| Severity | Medium |
| Kategori | A07:2021 Identification and Authentication Failures |
| Status | CONFIRMED (dinamis, `curl` 4 sampel per kasus) |
| Lokasi | `app/Http/Controllers/Web/DashboardLoginController.php:53,95-100`, `app/Actions/Auth/LoginWithPassword.php:30,62-67` |

**Root cause.** `dummyHash()` menyimpan hash di variabel `static`, padahal PHP (FPM/CLI server) mereset state setiap request.
Untuk email yang tidak terdaftar, setiap request menjalankan `Hash::make()` + `Hash::check()` (2× bcrypt). Email terdaftar hanya
menjalankan `Hash::check()`. Komentar "agar waktu respons sama" tidak terpenuhi.

**Bukti (lokal).**

| Endpoint | Email terdaftar, sandi salah | Email tidak terdaftar |
|---|---|---|
| `POST gspos.localhost/login` | 0,254–0,256 s | 0,490–0,515 s |
| `POST api.gspos.localhost/v1/auth/login` | 0,256–0,287 s | 0,490–0,491 s |

**Dampak.** Penyerang tanpa autentikasi bisa memastikan email owner/manager terdaftar dengan selisih ~2× yang mudah dibedakan.
Hasilnya jadi bahan phishing atau credential stuffing (diperparah SEC-004). Ini meniadakan kontrol anti-enumerasi yang tercatat
di bagian 6.

**Rekomendasi.** Pakai hash dummy konstan yang sudah dihitung sebelumnya dengan cost yang sama (mis. konstanta atau
`config('pos.auth.dummy_hash')` hasil `Hash::make` saat deploy), atau `Cache::rememberForever`. Tambahkan test unit yang memastikan
`Hash::make` tidak dipanggil di jalur login (spy `Hash`).

**Test regresi.** `GspoSec010LoginTimingTest.php` (rencana): `Hash::spy()`, login email tak dikenal, dan pastikan `make` tidak dipanggil.

### GSPOS-SEC-011 — User multi-outlet bisa membayar/mengubah open bill outlet lain

| Field | Isi |
|---|---|
| Severity | Medium |
| Kategori | API1:2023 BOLA / Bug logika (rekonsiliasi kas) |
| Status | **CONFIRMED (PoC)** |
| Lokasi | `app/Support/CurrentOutlet.php:52-62` (`accessibleIds()` = `user->outletIds()`), `app/Actions/Order/AddPayment.php:53-69`, `app/Actions/Order/SaveOpenBill.php:45-57`, `app/Http/Controllers/Api/V1/OrderController.php:86-101` |

**Root cause.** Untuk token user, `OutletScope` mengizinkan **semua outlet yang dipegang user**, bukan hanya outlet perangkat.
`addPayment`/`void` memakai route binding tanpa `Gate::authorize`. `SaveOpenBill` memakai `Idempotency::existing()` yang membuang
semua scope. `OrderWriter::complete()` memindahkan order ke shift perangkat tanpa mengecek `shift.outlet_id === order.outlet_id`.

**Dampak.** Owner, atau manager yang memegang outlet A+B, login di perangkat outlet B lalu melunasi atau mengubah open bill
outlet A. Hasilnya:
- order tercatat di outlet A, tetapi `shift_id` = shift B;
- `expected_cash` shift B ikut menghitung order A;
- stok berkurang di A, sementara uang ada di laci B;
- item open bill A bisa diganti dari outlet lain.

**Reproduksi.** `GspoSec011CrossOutletOrderMutationTest.php`:
- `POST /orders/{billA}/payments` dari device B → **201** ✗
- `PUT /orders/{billA}` dari device B → **200** ✗

**Rekomendasi.**
- Di `AddPayment`, `SaveOpenBill`, dan `VoidOrder`: tolak dengan `NOT_FOUND` bila `order.outlet_id !== CurrentOutlet::selectedId()`
  (outlet perangkat).
- Untuk request dengan perangkat, pertimbangkan agar `CurrentOutlet::accessibleIds()` mengembalikan hanya outlet perangkat.
- Tambahkan `Gate::authorize('view', $order)` di controller.

**Test regresi.** `GspoSec011CrossOutletOrderMutationTest.php` hijau, ditambah varian void.

### GSPOS-SEC-014 — Batas diskon supervisor tidak pernah berlaku

| Field | Isi |
|---|---|
| Severity | Medium (kontrol yang tampak ada tetapi tidak berfungsi) |
| Kategori | A04:2021 Insecure Design / Bug logika |
| Status | CONFIRMED (kode + test `CheckoutTest.php:308` "supervisor sendiri boleh diskon di atas batas tanpa approval") |
| Lokasi | `app/Enums/UserRole.php:78` (`Supervisor => ['order.*', ...]`), `app/Actions/Order/PriceOrder.php:57-71`, `app/Actions/Auth/VerifyApproval.php:29`, `app/Http/Requests/Api/V1/Outlet/OutletSettingsRequest.php:40` |

**Root cause.** SPEC Q18: "role dengan `order.discount_over_limit` tidak dibatasi". Supervisor mendapat permission itu lewat
wildcard `order.*`, sehingga `VerifyApproval` langsung `return null`. Padahal SPEC §199 mencontohkan
`{"cashier": 10, "supervisor": 25}`, dan owner bisa mengatur `discount_limits.supervisor` lewat API maupun dashboard.

**Dampak.** Owner mengira supervisor dibatasi 25%. Kenyataannya supervisor bisa memberi diskon hingga 100% tanpa PIN, dan

### GSPOS-SEC-015 — TrustProxies tidak dikonfigurasi

| Field | Isi |
|---|---|
| Severity | Medium |
| Kategori | A05:2021 |
| Status | PLAUSIBLE (tergantung topologi cPanel/Cloudflare) |
| Lokasi | `bootstrap/app.php:35-60` (tanpa `trustProxies`), `app/Support/Domains.php:58-68`, `app/Http/Middleware/SecurityHeaders.php:35`, `public/.htaccess:29` |

**Dampak bila TLS diputus di proxy.**
- `isSecure()` = false, sehingga HSTS tidak pernah terkirim.
- `Domains::url()` memakai skema request, sehingga redirect tiket login/signup bisa memakai `http://`.
- `$request->ip()` = IP proxy, sehingga semua limit per IP (auth, PIN, signup, contact) dipakai bersama oleh semua pengguna. Akibatnya bisa terjadi lockout massal sekaligus brute force yang lebih longgar.
- `.htaccess` menganggap request aman bila client mengirim `X-Forwarded-Proto: https` (header dikontrol client).

**Rekomendasi.**
- `$middleware->trustProxies(at: [IP/CIDR proxy], headers: X_FORWARDED_FOR | X_FORWARDED_PROTO)` sesuai produksi.
- Paksa `https` di `Domains::url()` saat production.
- Verifikasi HSTS di produksi.
- Hapus kondisi `X-Forwarded-Proto` di `.htaccess` bila tidak ada proxy tepercaya.

## 6. Kontrol yang Sudah Baik (diverifikasi)

**Kode**
- `TenantScope` fail-closed; `tenant_id` tidak fillable dan dikunci saat create/update. `OutletScope` fail-closed untuk user tanpa outlet.
- `SetTenantContext`, `EnsureUserToken`, `EnsureDeviceToken` berjalan sebelum `SubstituteBindings`.
- `Gate::before` hanya untuk permission terdaftar; mode hanya-baca (ADR 0009).
- PIN & password `hashed`; lockout atomik `lockForUpdate`. Self-approval ditolak.
- Token dicabut saat role/password/PIN berubah lewat `SaveEmployee` dan saat reset password; device dicabut → token ditolak.
- Nominal order dihitung ulang server dengan bcmath skala 2. Opsi wajib milik grup produk; min/max select ditegakkan.
  Produk/opsi/metode bayar nonaktif atau tidak dijual di outlet ditolak. Non-tunai tidak boleh melebihi sisa tagihan.
- Shift: satu shift terbuka per device (unique `open_device_key`). Tutup shift memakai lock dan idempoten. Void idempoten.
- Panel admin: guard `admin` terpisah (tabel `admins`), 2FA wajib dicek per request, tanpa impersonation, tenant tidak bisa dihapus.
- Dashboard: hanya owner yang punya `user.manage`/`outlet.*`/`payment_method.manage`; owner terakhir dilindungi;
  `OutletSettings` `#[Locked]` + cek ulang; global search hanya resource ber-scope; export dibatasi `report.export`, rentang ≤ 366 hari, `SafeCell`.
- XSS: tidak ada `{!! !!}`, `x-html`, `Str::markdown`, RichEditor; struk meng-escape semua field; `@js()` aman; label di `HtmlString` di-escape.
- Upload gambar produk: whitelist `image/jpeg|png|webp` (tanpa SVG), ≤ 1 MB, direktori per tenant, `hashName()`, temp upload Livewire private.
- Signup/contact: hanya `validated()` (tanpa mass assignment), status `Trial` hardcode, contact menyimpan IP sebagai HMAC, tidak mengirim email.
- CORS tanpa origin default, `supports_credentials=false`; Sanctum bearer saja (`guard => []`).
- Log tidak memuat PIN/password/token; `dontFlash` lengkap. `.htaccess` memblokir dotfile/`.env`/`.log`/`.json`.

**Dinamis (curl, lokal)**
- Header di semua host: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, COOP;
  API: `CSP default-src 'none'`, `Cache-Control: no-store`. `X-Powered-By` dihapus.
- Cookie sesi `HttpOnly; SameSite=Lax`, host-only per subdomain (Secure tidak aktif karena HTTP lokal; pastikan `SESSION_SECURE_COOKIE=true` di produksi).
- CSRF: `POST /login` dan `POST switch-outlet` tanpa token → **419**.
- Login web: pesan sama untuk email tak terdaftar & sandi salah (tetapi lihat SEC-010 untuk timing).
- Tiket login sekali pakai, session ID berganti setelah redeem (anti session fixation).
- Outlet switcher: outlet tenant lain → **404**; outlet tenant sendiri yang tidak ditugaskan ke manager → **404**.
- Manager: `/settings/employees|outlets|payment-methods|outlet` → **403**; `/orders/{uuid acak}` → **404**.
- Cookie sesi tenant dikirim ke `admin.` → redirect `/login` (guard terpisah).
- `/.env`, `/.git/HEAD`, `/composer.json`, `/vendor/*`, `/telescope`, `/_ignition/*` → 404; `/storage/logs/laravel.log` → 403.
